# Decision Log (append-only)

Format: ID · date · decision · rationale · alternatives rejected · evidence.

**D-001 · 2026-11-05 · Central repository keyed by portal identity, not by user/project.**
`permits` unique `(adapter_key, portal_record_id)` (DC: ProjectDox ProjectID). Rationale: dashboard `launchRemote` and ProjectDox deep links share the ProjectID space (observed). Rejected: `permit_number + user_id` matching (current `syncPortalDataToSupabase`, line ~3589) — breaks with multiple accounts.

**D-002 · 2026-11-05 · Daily full metadata refresh; downloads/reports gated by change.**
28 permits × ≤6 sections is cheap; fingerprint-gating adds complexity with no benefit at this scale. Revisit above ~200 permits per source. Rejected: fingerprint-gated deep scrape.

**D-003 · 2026-11-05 · JSON API first, DOM fallback, per section — subject to Phase 0 verification.**
Evidence: PGC scraper uses `ProjectDoxWebAPI/*`; DC page JS uses `Globals.ApiUrl` endpoints (`raw_frame_0.html`).

**D-004 · 2026-11-05 · Additive queue (`permit_sync_jobs`/`permit_sync_events`) instead of modifying `scrape_jobs`.**
`scrape_jobs.project_id`, `scrape_events.project_id`, `scrape_file_results.project_id` are NOT NULL and are read by existing UI/realtime progress and Arlington RPCs. Making them nullable risks regressions in code paths that assume a project. Copy the proven lease pattern (`claim_arlington_scrape_job`) into new RPCs. Rejected: generalizing `scrape_jobs` (regression risk), pgmq/Redis (new infra).

**D-005 · 2026-11-05 · Automation config in additive `permit_sync_sources` table, not new columns on `portal_credentials`.**
Avoids touching credential RLS/grant code; admin-only table; FK to credential.

**D-006 · 2026-11-05 · Default-deny visibility with credential provenance; project links grant nothing.**
Access = admin OR credential grant on a source credential OR explicit `permit_access_grants`. Rejected: reusing `_user_has_scraped_data_scope` (returns TRUE when a user has no scopes) and governance `assert_*` (no-op in `legacy` mode).

**D-007 · 2026-11-05 · One worker job per source credential run with checkpoint cursor.**
Login/SSO is the fragile, DOB-visible step; per-permit jobs multiply logins. Concurrency: max one active job per source.

**D-008 · 2026-11-05 · Separate Railway service, same image, new entrypoint.**
Playwright memory isolation from interactive manual scrapes; existing worker runs inside the HTTP process (`server.js` → `registerExecutionRoutes`). New entry does not load `register-execution-routes.js`.

**D-009 · 2026-11-05 · Rollback = disable, never drop collected data.**
Order: cron off → sources `automation_enabled=false` → worker scaled to 0 → feature flag off. Schema reversals only via reviewed forward migrations after export.

**D-010 · 2026-11-05 · Real-Postgres SQL tests via PGlite (devDependency of scraper-service).**
No local Postgres server or running Docker on the dev machine; existing queue tests are in-memory simulations. PGlite (Postgres 16.4 WASM) verified to enforce RLS with `SET ROLE`. Supabase objects (`auth.uid()`, roles, storage) are stubbed in a test harness.

**D-011 · 2026-11-05 · Writes via one transactional service-role RPC per permit batch; diff computed in JS.**
JS differ is unit-testable against fixtures; the RPC applies upserts, snapshots and change rows atomically. Rejected: DB triggers (opaque), plpgsql diffing (hard to test).

**D-012 · 2026-11-05 · Integrity guard: never overwrite with suspicious empties.**
A section returning zero items where the previous capture had items, without an explicit portal "0 records"/absent-tab signal, is treated as a parse failure; prior rows are retained and the section is marked stale.

**D-014 · 2026-11-05 · DC: metadata only, no file downloads.** _(Superseded 2026-11-11 by D-056.)_
The Commun-ET account has `DownloadFile: false` on observed folders, and the dashboard "Download Files" control is denied by the safety guard. Store file metadata (name, version, status, dates, size, review cycle) only. Revisit only with a different credential and approval.

**D-015 · 2026-11-05 · Supersedes the "diff computed in JS" half of D-011: the database computes diffs.**
`apply_permit_sync_batch` compares each keyed item with the stored row after normalising values through the column types (`jsonb_populate_record`), so timestamps and numbers compare equal regardless of input formatting. JS shapes items, hashes them and applies integrity guards; it never decides what changed. Rationale: one authoritative comparison inside the same transaction as the write, safe under concurrent runs, and no stale client-side "previous" state. Tested on real Postgres (PGlite). Rejected: JS differ (needs a prior read per permit, races with concurrent runs).

**D-016 · 2026-11-05 · Section status semantics and null handling (refines D-012).**
Per section: `ok` = full listing (upsert, soft-remove unlisted rows); `partial` = upsert only; `absent` = portal does not offer it; `failed` = extraction error; the DB downgrades an `ok` section with zero items to `suspect_empty` while active rows exist unless `confirmed_empty` is set. Only `ok` removes. Removal is soft (`removed_at`), and a reappearing row is `restored`. Null permit fields are stripped before apply, so a missing value never blanks a stored one. Sections whose item count disagrees with an independent portal count (e.g. unresolved comments in the status JSON) are downgraded to `partial` by `core/ingest.js`.

**D-017 · 2026-11-05 · Offset-less portal timestamps are America/New_York wall-clock time.**
Reviews rows and observed JSON dates carry no offset. The normalizer converts them to UTC (DST-aware) instead of letting Postgres read them in the server zone (UTC on Supabase, a 4–5 h error). Confirmed 2026-11-06: JSON, report and Reviews tab share one clock, and the report's "Report Generated" time is America/New_York (EST observed; EDT inferred from the zone). See `DC_DEEP_EXTRACTION_REQUIREMENTS.md` §3.9.

**D-018 · 2026-11-05 · One automation driver per portal login.**
`portal_credentials` is one row per permit (`permit_number` is NOT NULL since 20260220000000), so several rows can share the DC login. `admin_set_permit_sync_source` refuses to enable automation on a second credential with the same jurisdiction + username. The repository itself is account-level: `permit_source_links` maps one credential to every permit it sees.

**D-019 · 2026-11-05 · Backward compatibility proven by replaying the real migration chain.**
`tests/helpers/replay-migrations.js` applies all migrations on PGlite with a minimal Supabase baseline and stand-ins for pg_cron, pg_net, Vault and pgcrypto (pgvector is real). The chain test fingerprints every pre-existing column, policy, trigger, function body/ACL and table ACL before and after the new migration and requires them identical. One data-only migration (`20260817160000_reset_highland_springs_package_review.sql`) is skipped because it asserts a production row. Finding (pre-existing, not changed): `20260911200000_super_admin_hierarchy.sql` adds an enum value and uses it in the same file, which fails when the file runs as one transaction on a fresh database; the replay adds the value first.

**D-020 · 2026-11-05 · Evidence is append-only, including against the service role.**
Row triggers block UPDATE/DELETE on `permit_snapshots` and `permit_changes`; statement triggers block TRUNCATE (which bypasses row triggers); the service role has only SELECT/INSERT on them; permits referencing evidence cannot be deleted (FK RESTRICT). A deliberate purge requires the session setting `permit_repo.allow_evidence_purge = on` as table owner.

**D-021 · 2026-11-06 · Queue: Arlington-style leases, one active job per source, no cron.**
`permit_sync_jobs` holds at most one non-terminal job per credential (partial unique index). Workers claim with `FOR UPDATE SKIP LOCKED` and a TTL lease; heartbeat and finish check the holder, so a reclaimed or cancelled job cannot be overwritten by the old worker. Expired leases are reclaimed; a lease that expires on the last attempt fails the job (`lease_expired`). Retries back off 300·2^(attempt−1) s; rate limits default to 1 h. MFA/CAPTCHA put the source in `waiting_user` until an admin resumes it; two consecutive auth failures put it in `auth_failed`. `enqueue_permit_sync_runs()` exists but nothing schedules it (A-4). Rejected: reusing the Arlington tables (different payload, and Arlington must not regress).

**D-022 · 2026-11-06 · Live DC transport: two request policies, explicit API checks, no retry of login.**
Login and the `launchRemote` SSO hop use an auth policy (identity-provider hosts may receive POSTs; DC hosts only GET plus a short OIDC callback list; deny patterns still apply except the SessionEnded landing page). All other browser traffic uses the read guard. Off-host requests (analytics, CDNs) are aborted without counting as violations because they cannot touch portal data; static assets are allowed. `context.request` bypasses `context.route`, so every API call is checked against the guard before it is sent, with redirects disabled. The password is submitted at most once per job; a second login form raises `auth_failed`. The context is closed instead of clicking Log Out. Reviews, Info, Reports and the SSRS report throw `not_implemented` until their parsers are verified live, so those sections are `failed` and write nothing. Status: Implemented, never run live (A-3).

**D-023 · 2026-11-06 · Click guard allows the dashboard pager and launchRemote, nothing broader.**
Pager links are allowed only as `<a href="javascript:void(0)">` with no inline handler and text that is a page number or Next/Prev/First/Last. `launchRemote` is allowed only when the whole handler is `launchRemote('Project/Index?tab=<word>&ProjectID=<digits>')` (optionally `return false`) and the other attribute is empty, `#` or `void(0)`; the target must pass the request guard as `project_page`. Request allowlist adds `dashboard_home` (`/`) and `sso_hop` (`/login/sso?url=Project/Index?...`), both observed in Phase 0. Unverified: the legacy reader's comment mentions `launchRemote('Frame.aspx?...')`; such links are refused, which fails the run safely rather than widening the rule.

**D-024 · 2026-11-06 · Encrypted-credential check matches the real envelope.**

**D-039 · 2026-11-11 · Approved by the user ("delete_fix"): job events may be deleted only by the cascade from deleting their source credential or source row. Narrows D-020 for `permit_sync_events` only.**
`permit_sync_events` uses its own guard (`_permit_sync_events_guard`): a row may be deleted only inside a foreign-key cascade (`pg_trigger_depth() > 1`) and only when its job row no longer exists. `permit_sync_jobs` gets a delete guard of the same kind: a job may be deleted only in a cascade after its `permit_sync_sources` row is gone. So the only paths that remove events are deleting the `portal_credentials` row (the app's `DELETE /api/portal-credentials/:id`) or the source row, or the owner purge setting (D-020). UPDATE stays blocked; TRUNCATE is blocked by statement triggers on both tables (events previously relied on privileges only). `permit_snapshots` and `permit_changes` keep the unchanged D-020 trigger; deleting a credential removes its `permit_source_links` but leaves permits and evidence. Why both conditions: `pg_trigger_depth() > 1` alone also passes a DELETE issued from any other trigger (mutation test: a trigger-nested `DELETE FROM permit_sync_events` succeeded), and the parent-gone check alone would let the service role, which holds DELETE on `permit_sync_jobs`, erase a job's events by deleting the job. A direct DELETE cannot meet the parent-gone condition because the foreign key keeps the parent alive while children exist. Rejected: a session flag set by the delete route (the route uses supabase-js over PostgREST, which cannot set it in the same transaction); `ON DELETE SET NULL` on events (orphans events and still needs an UPDATE exception). Tests: `permit-sync-queue.test.js` "deleting the source credential cascades…", `permit-repo-ingest.test.js` "deleting the source credential keeps permits…"; both fail against the old trigger.
